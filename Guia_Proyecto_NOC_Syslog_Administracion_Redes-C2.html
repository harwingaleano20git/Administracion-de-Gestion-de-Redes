Requisitos funcionales mínimos

  1. RF-01: registrar y editar inventario de dispositivos.
  2. RF-02: recibir o importar mensajes Syslog.
  3. RF-03: normalizar fecha, IP, marca, severidad y mensaje.
  4. RF-04: visualizar estado, eventos e incidentes.
  5. RF-05: abrir, asignar, actualizar y cerrar incidentes.

Requisitos no funcionales mínimos

  1. RNF-01 Seguridad: secretos fuera del código.
  2. RNF-02 Usabilidad: navegación comprensible sin manual extenso.
  3. RNF-03 Trazabilidad: cada evento e interacción tiene fecha y actor.
  4. RNF-04 Confiabilidad: errores controlados y bitácora.
  5. RNF-05 Portabilidad: instalación documentada desde cero.
  6. RNF-06 Mantenibilidad: módulos, nombres claros y comentarios útiles.
  7. RNF-07 Rendimiento: el tablero no se bloquea con el volumen de prueba.
  8. RNF-08 Recuperación: copia y procedimiento de rollback.

Laboratorio administrado

Syslog desde cero

Syslog comunica eventos entre un originador, posibles relays y un colector. La severidad va de 0 —más urgente— a 7 —depuración—. UDP/514 es común en laboratorio, pero no confirma entrega ni protege el contenido; cuando los equipos lo permitan, prefiera un transporte seguro y autenticado.

1. Colector de laboratorio en Ubuntu/Debian

Servidor · comandos comentados
# Actualiza el índice de paquetes; no modifica los equipos de red
sudo apt update

# Instala rsyslog, servicio que recibirá y almacenará eventos
sudo apt install -y rsyslog

# Crea un archivo de configuración exclusivo para recepción remota
sudo nano /etc/rsyslog.d/10-noc-remoto.conf

# --- Contenido del archivo ---
module(load="imudp")                 # carga recepción UDP
input(type="imudp" port="514")      # escucha Syslog UDP/514
$CreateDirs on                       # permite crear carpetas dinámicas
template(name="PorEquipo" type="string"
 string="/var/log/noc/%HOSTNAME%/syslog.log")
*.* action(type="omfile" dynaFile="PorEquipo")
# --- Fin del archivo ---

# Verifica sintaxis antes de reiniciar
sudo rsyslogd -N1

# Reinicia y revisa el servicio
sudo systemctl restart rsyslog
sudo systemctl status rsyslog --no-pager

# Confirma que existe un proceso escuchando UDP/514
sudo ss -lunp | grep ':514'

# Observa tráfico de laboratorio; Ctrl+C para terminar
sudo tcpdump -ni any udp port 514

Firewall: abra UDP/514 únicamente desde las subredes o IP de los dispositivos autorizados. Si el colector funciona como servicio productivo, diseñe autenticación, cifrado, rotación, integridad, respaldo y capacidad.

No es “un cuadro que ejecuta cualquier cosa”

La versión segura tiene dos capas: el navegador muestra la interfaz; un backend autorizado maneja SSH con Netmiko/Paramiko u otra biblioteca. Las credenciales nunca se guardan en HTML ni se envían al modelo de IA.

Controles para v1.0

  • Inventario de hosts permitidos y verificación de huella SSH.
  • RBAC: lector, operador y administrador.
  • Secretos en variables de entorno o gestor de secretos.
  • Timeout, límite de intentos y bloqueo de comandos arbitrarios.
  • Backup y diff antes de un cambio; rollback documentado.
  • Registro íntegro: quién, qué, cuándo, equipo, resultado.

Prohibido: conectarse a equipos o redes sin autorización; guardar contraseñas, tokens o claves privadas en GitHub; permitir que un agente de IA ejecute comandos de cambio sin validación humana; usar salidas de dispositivos como instrucciones para la IA.

Integración Telegram desde cero · Corte 3

  1. En Telegram busca la cuenta verificada @BotFather.
  2. Envía /newbot, asigna nombre y un usuario terminado en bot.
  3. Guarda el token como secreto. No lo pongas en capturas, código ni GitHub.
  4. Abre conversación con el bot y pulsa Start.
  5. Obtén el chat_id desde una prueba local controlada y guárdalo como variable de entorno.
  6. Programa alertas solo para incidentes definidos por política; agrega deduplicación y límite de frecuencia.

Git guarda la historia; GitHub la publica

Un repositorio contiene archivos e historial. Una rama es una línea de trabajo separada. Un commit es una fotografía explicada de un cambio. Una pull request propone integrar una rama. README.md explica qué es, cómo instalar y cómo probar el proyecto.

Prompt maestro · versión alfa

La IA entrega una base; tú entregas un sistema

El prompt adapta la metodología 4-D: deconstruir, diagnosticar, desarrollar y entregar. Está diseñado para distintos asistentes de IA. Pide razonamiento interno, pero exige como salida decisiones, supuestos, pruebas y código; no cadenas de pensamiento privadas.

1 · Deconstruir

Objetivo, usuarios, entradas, salidas, restricciones y faltantes.

2 · Diagnosticar

Ambigüedades, riesgos, dependencias y criterios de aceptación.

3 · Desarrollar

Arquitectura simple, módulos pequeños, seguridad y pruebas.

4 · Entregar

Árbol de archivos, código completo, comandos y verificación.

Uso correcto: ejecuta una fase a la vez. Después de cada archivo, pide: “explícame qué hace, cómo lo pruebo, qué salida espero y cómo revierto el cambio”. Copiar sin probar no constituye evidencia.

Seguridad por diseño

Defender la red y también al asistente de IA

Un agente puede leer logs, sugerir acciones o invocar herramientas. Por eso, cada entrada externa se trata como dato no confiable y cada capacidad se limita por identidad, alcance y aprobación.

Identidad y secretos

  • RBAC y mínimo privilegio.
  • MFA para GitHub y cuentas de operación.
  • Tokens en gestor de secretos o .env.
  • Rotación y revocación documentadas.

Comandos y herramientas

  • Allowlist por marca y rol.
  • Vista previa y diff.
  • Aprobación humana para cambios.
  • Timeout, rate limit y kill switch.

Datos y logs

  • Validar y escapar entradas.
  • Sin credenciales en mensajes.
  • Integridad, retención y acceso.
  • Separar datos reales y sintéticos.

Política mínima de Syslog

  • Fuentes autorizadas e inventariadas.
  • NTP y zona horaria coherentes.
  • Umbral por ambiente y fabricante.
  • Transporte seguro cuando sea compatible.
  • Retención definida por necesidad y norma.
  • Acceso por rol y auditoría de consulta.
  • Rotación, capacidad, respaldo e integridad.
  • Mapeo severidad → responsable → tiempo.
  • Evitar datos personales/secretos innecesarios.
  • Prueba periódica de recepción y recuperación.

Reglas de evidencia

  1. Las capturas deben ser legibles, numeradas y tener un pie que indique qué prueban.
  2. El código mostrado debe coincidir con el repositorio y la versión entregada.
  3. No se aceptan secretos visibles ni evidencias de infraestructuras no autorizadas.
  4. Datos sintéticos deben estar marcados; datos reales, anonimizados cuando corresponda.
  5. Si una función no puede reproducirse, se valora como parcial aunque exista una captura.
